The OpenTelemetry Transformation Language (OTTL) is now v1. The project [announced on 2026-10-27](https://opentelemetry.io/blog/2026/ottl-v1/) that, starting with opentelemetry-collector-contrib v0.164.0, OTTL is stable for traces, metrics, and logs. OTTL is the statement language of the transform and filter processors, and 12 other contrib components accept it too, including the routing connector and the tail sampling processor{% include cite.html n=1 %}.

## What the guarantee covers

For all of 1.x, the syntax in the language reference is frozen: paths, literals, operators, function calls, and `where` clauses. New syntax can arrive in a minor release, but existing syntax won't be removed or change meaning{% include cite.html n=1 %}. No function in the standard set will be removed or have its signature changed incompatibly. The Go API for components built on OTTL also stays compatible{% include cite.html n=1 %}. A statement that parses against one 1.x release will parse and behave the same against every later one{% include cite.html n=1 %}.

## What sits outside it

New functions now start out as experimental, in the `xottl` module. That module is versioned at 0.x, so its functions can change or disappear in any release. Statements that use them parse only when the `pkg.ottl.functions.enableExperimental` feature gate is on{% include cite.html n=1 %}. To be promoted to the standard set, a function needs at least two minor releases as experimental, complete tests and documentation, no open proposals to change it, and demand from users{% include cite.html n=1 %}.

The lambda-powered functions (`Filter`, `MapEach`, `MapKeys`, `Any`, `All`, `Find`, `Reduce`, and `When`) are experimental and still require the `ottl.functions.enableLambda` gate{% include cite.html n=1 %}. Profiles support is still in development and has moved to a separate `xprofile` module, also at 0.x. Experimental Go APIs such as `SliceGetter` live in `xottl`{% include cite.html n=1 %}.

The components that ship with contrib, including the transform and filter processors, register the experimental functions but leave them off by default. Enabling the matching gate is enough; no custom build is needed{% include cite.html n=1 %}.

## What to do

- **Remove retired gates.** Ahead of v1 the project removed gates that had reached stable, including `ottl.PanicDuplicateName` and `ottl.contexts.enableOTelColContext`, and v0.164.0 removes `ottl.set.allowNil`. The project says to stop passing any of these to the Collector before you upgrade{% include cite.html n=1 %}. The [v0.164.0 release notes](https://github.com/open-telemetry/opentelemetry-collector-contrib/releases/tag/v0.164.0) also remove the filter processor's stable `processor.filter.defaultErrorModeIgnore` gate.
- **Look for removed functions.** Long-deprecated functions such as `Base64Decode`, and the old profile functions, are gone{% include cite.html n=1 %}.
- **Find statements that need a gate.** Search transform and filter configs for the lambda-powered functions listed above. Each one's entry in the [experimental functions reference](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/b21bf1a21be57988b655aa03ff664dbb250d6a99/pkg/ottl/xottl/ottlfuncs/README.md) says it requires `ottl.functions.enableLambda`. The OTTL [feature-gate table](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/b21bf1a21be57988b655aa03ff664dbb250d6a99/pkg/ottl/documentation.md#feature-gates) says experimental functions are rejected unless `pkg.ottl.functions.enableExperimental` is on. The documentation doesn't say whether the lambda functions need that gate as well, so validate any config that uses them against v0.164.0 before rolling it out.
- **Skipping releases?** Read the contrib changelog's `pkg/ottl` entries between your version and v0.164.0{% include cite.html n=1 %}.
