Amazon Aurora MySQL-Compatible Edition 8.4 now supports MySQL 8.4.10, AWS [announced](https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-aurora-mysql-8410-available/) on 2026-11-02. The release allows up to 50,000 simultaneous connections per DB instance. AWS says that lets connection-heavy applications scale without a connection pooling layer{% include cite.html n=1 %}. AWS also recommends the upgrade to pick up fixes for CVEs in earlier MySQL versions, as well as community bug fixes{% include cite.html n=1 %}.

## What changed

The [8.4.10 release notes](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraMySQLReleaseNotes/AuroraMySQL.Updates.8410.html) say the highest allowed `max_connections` value rises from 16,000 to 50,000. The release also adds tagged global transaction identifiers (GTIDs) in the form UUID:TAG:NUMBER, so transactions from one source server can be grouped by workload in replication{% include cite.html n=2 %}. It adds `RETURNING` for single-table `DELETE` statements. `RETURNING` is now a reserved keyword, so identifiers named `returning` must be quoted with backticks{% include cite.html n=2 %}. Minor upgrades from 8.4.7 or 8.4.8 complete faster{% include cite.html n=2 %}.

## What sets your limit

The 50,000 figure is a maximum, not a default. The [Aurora User Guide](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.Managing.Performance.html) says the limit comes from `max_connections` in the instance's parameter group, and the default value depends on the instance class. As of 2026-11-03, those defaults range from 45 on db.t3.small to 8,000 on db.r7i.48xlarge and db.r8g.48xlarge{% include cite.html n=3 %}. You can raise the limit by moving to a class with more memory or by setting a larger `max_connections`{% include cite.html n=3 %}. The cap is 50,000 on 8.4.10 and higher, and 16,000 on all other versions{% include cite.html n=3 %}.

For more than 16,000 connections, AWS recommends a 24xlarge or larger class. It warns that every connection, even an idle one, uses memory and CPU, and that a very large number of connections on smaller classes can raise query latency significantly{% include cite.html n=3 %}. It also advises sizing for the peak number of connections that are active at the same time, and opening connections gradually{% include cite.html n=3 %}. For applications that open and close connections often or hold many long-lived ones, the same guide still recommends Amazon RDS Proxy, a pooling proxy{% include cite.html n=3 %}.

## How to upgrade

Upgrades can come through automatic minor version upgrades in maintenance windows. AWS Organizations' Upgrade Rollout Policy can phase them across clusters. Minor upgrades work in place or by restoring a snapshot{% include cite.html n=1 %}. Aurora MySQL 8.4.10 is available in all Regions where Aurora MySQL is offered{% include cite.html n=1 %}.

## What to do

- **Check before removing a pooler.** Look up your instance class's default `max_connections` and the value in your parameter group. Going past the default means setting the parameter yourself{% include cite.html n=3 %}.
- **Size the instance.** Above 16,000 connections, AWS recommends 24xlarge or larger, sized for peak active connections{% include cite.html n=3 %}.
- **Search your schema for `returning`.** Tables, columns, or aliases with that name need backticks after the upgrade{% include cite.html n=2 %}.
- **Phase the rollout.** Test on lower-priority clusters first, which is what the Upgrade Rollout Policy is designed for{% include cite.html n=1 %}.
